## 1. 三部分的职责（单一归属原则）

接口/存储契约以当前实现为准，报告对原始实测负责。skill 可以保留完成路线所需的
最小调用示例与决策字段，但不另维护一套完整工具手册；案例必须携带其条件和证据边界。

| 部分 | 只负责 | 明确不负责 |
|---|---|---|
| **skill** | 可执行的方法：触发条件、最小调用、预期结果、验证、失败分支、恢复与停止条件 | 不把单次应用实测推广为普遍能力，不复制整份工具手册 |
| **memory** | 可复用路线：版本、页面/控件、启动和保护条件、步骤、失败边界、证据指向与可信度 | 不代替原始日志，也不把条件剥离后只留“可用/不可用” |
| **MCP** | 执行与读回：把动作可靠地做出来，并如实报告"做了什么/没做什么" | 不判断业务语义、不替调用方决定该信哪条路线 |

一句话：**skill 说"怎么做"，memory 说"这个应用能不能这么办"，MCP 说"这次办了没"**。

## 2. skill：原则必须落实为可执行步骤

### 2.1 保留（原则与判断流程）

- 四级路线顺序（后台高效 → 后台低效 → 前台高效 → 前台低效）及降级理由要求
- 调用前防抢焦的验收条件、失效判定、退出条件
- 基础探测：区分"未试 / 权限不足 / 工具缺失 / provider 报错 / 执行了但没效果"
- 效果验证原则：返回值、元素数、像素、业务标志各自能证明什么
- 任务范围与路线台账的字段要求
- 写 memory 的规则（正文八节、保留失败与未试方向）
- 每条常见路线的“触发 → 具体操作 → 预期 → 验证 → 失败分支 → 停止/恢复”操作卡。
- 少量完整工具调用示例，说明从哪个现场字段取得参数；示例值不得冒充现场事实。
- 影响下一步判断的已知缺口，以及工具缺失、权限受阻、执行未知时可继续的调查。
- 有版本、条件和来源的反例，用来解释错误判断；安装版 skill 不能只剩不可访问的仓库链接。

### 2.2 按用途组织详细内容

| 内容 | 现位置 | 移到 |
|---|---|---|
| 原始请求、完整计数和测量过程 | 报告与日志 | skill 保留足以判断适用范围的案例、来源与反例 |
| 启动 flag 对照 | 报告保存实测，工具参考保存当前追加参数 | skill 说明如何核对活动进程、单变量对照与回退 |
| 完整参数表和所有返回字段 | `references/tool-reference.md` | skill 操作卡保留完成当前路线所需的最小 JSON 和决策字段 |
| `find_items` 的参数边界 | 工具参考 | skill 必须给出首批、重叠页、游标不前进、错误字段和全量核对的步骤 |
| 历史反例 | 按诊断用途归入相关路线 | 保留条件，去掉重复转录，不能删掉失败和未试方向 |

### 2.3 拆分后的结构

```text
skills/windows-app-automation/
  SKILL.md                     # 主流程、决策表、具体操作卡与完整示例
  references/
    foreground-protection.md   # 保持：保护机制的调查与验收
    tool-reference.md          # 新增：每个工具的参数、返回值、已知缺口
  scripts/                     # 保持
```

验收按操作是否可执行，不限制任意行数，也不禁止有上下文的数字/版本。
历史测量须标明适用条件与来源；用来教学的页大小、索引和 JSON 参数可直接保留。

## 3. memory：按路线拆，一条一个结论

### 3.1 颗粒度

一条 plan = **一条可以判断适用性并重现的路线**。例如搜索框写入须一起保留版本、页面、
控件定位、原值、保护前提、写入/读回/恢复步骤与异步边界。不要为了拆成一个真假结论，
把安全复用所需的条件拆散。一次探测涉及不相关路线时再拆分。

### 3.2 正文形态

八节标题对"路线"仍然成立，但每节只写这条结论需要的最小内容：

```text
## 目标        这条路线要达成什么（一句话）
## 环境与适用条件  应用版本、窗口状态、启动条件
## 已验证步骤    编号步骤，每步写调用与预期
## 已尝试但失败  本路线实测失败的条件（没有就写"本路线未出现失败"）
## 实测记录      完整成本、覆盖率、副作用证据（指向仓库证据文件）
## 未解决       本路线仍不确定的部分
## 未试方向      本路线尚未覆盖的变体
## 更新记录      何时由谁验证/推翻
```

### 3.3 与应用实测的分工

- memory 存**结论与指路**：哪条有效、哪条无效、证据在仓库哪个文件。
- 原始 JSON、截图、脚本一律进仓库（`.superpowers/sdd/<日期>-<主题>/`
  或 `docs/reports/` 的附件目录），并在 plan 的「实测记录」里给出路径。
- memory 里不允许出现"完整测量过程"，那是报告的事。

|---|---|

完整召回核对条件/失败/未试方向，再带旧 revision 删除被取代的条目；不能先删后建。

## 4. MCP：可靠性的表达方式

工具不承诺"这个动作一定生效"，改为**如实分级报告**。三级：

| 级别 | 含义 | 现有字段 |
|---|---|---|
| 执行结果 | 调用到没到、provider 报没报错 | `ok` / `reason` / `execution_state` |
| 效果证据 | 有没有观察到界面真的变了 | `observation` / `route_effect` / 读回值 |
| 路线可信度 | 这条路线在该应用上被验证过几次 | **当前缺失** |

第三级是本轮要补的：memory 里有路线结论，但工具返回时不会带出来。
设计上**不自动推断**（自动匹配 memory 容易把旧版本结论套到新版本），
而是让调用方显式查（`recall`）后自己判断。MCP 侧只做一件事：
**保证前两级不说谎**：调用完成与效果已验证分别表达。`ok=true` 可以表示调用完成，
但不能据此声称业务目标达成；效果未知保留 `effect_verified=false` 及未知原因。
截图未变化、读回不可用或 provider 返回值都不能证明业务动作没有执行，不能因此重放。

### 4.1 已知缺口（不在本轮修，但要在文档里承认）

- 当前通用入口已接受同一 HWND 内、现场唯一定位的 `$control` 参数；它不是持久 COM 引用，
  不支持跨窗口、投影对象回传、NULL 续项或快照。ItemContainer 仍优先走 `find_items`。
- 某些已测控件不暴露可用 ScrollPattern；须按版本与容器确认，不能推成全部 Chromium 都不可用。
- 同一 API 在同一窗口内有的控件执行、有的不执行（导航按钮 vs 搜索行），
  工具无法在调用前判断

完整边界写入工具参考；在 skill 触发点同时给出判断和替代步骤，避免读者走到死路才发现缺口。

## 5. 怎么防止再次混淆

用测试而不是靠自觉。但这里有一个**必须先解决的冲突**：

### 5.1 修订前测试的问题

原测试曾要求正文包含具体历史数字，半成品改动又反过来禁止数字并限制行数。
这两种断言都不能证明操作指导有效，以下仅记录需要纠正的测试约束：

| 测试 | 断言 | 冲突 |
|---|---|---|
| `test_historical_numbers_are_marked_historical` | `assertIn("132")`、`assertIn("128")` | 要求正文保留历史节点数 |
| `test_untried_directions_survive` | 必须出现三个 `--disable-*` flag 名 | flag 名属于工具/启动文档，非方法 |
| `test_covers_every_surface` | 必须出现 UWP、Electron 等 | 可保留（属方法层面的界面分类） |
| `test_all_shipped_resources_are_reachable_inside_the_skill` | skill 目录下所有文件都必须被 md 链接到 | 新增 `references/tool-reference.md` 时必须同时加链接，否则失败 |
| `test_new_tool_names_are_the_real_ones` | 必须出现 7 个工具名 | 若工具手册移出，这条要改成指向 tool-reference |

**处置**：删除任意行数/禁数字测试，保留重要路线/授权边界与资源可达性检查，
忽略运行生成的 __pycache__。新增示例对真实 MCP schema 的校验，
再用独立操作者情境验证下一步决策。测试不过不能通过删除必要指导凑绿。

### 5.2 新增的约束测试

1. 文档中的最小工具调用通过实际 MCP schema 校验；资源链接在安装后的 skill 内可达，忽略缓存。
2. 用独立情境检查决策：执行未知不重放、私有桌面不等于 worker 已迁移、重叠分页保留同名项、
   文本截断不编造 offset、恢复前先核对当前状态与并发修改。
3. 代码回归检查用户可观察的最终内容/状态，包括正文花括号、非空旧文本、错误焦点、读回后缀、
   窗口重显、恢复失败可重试、卸载配置完整性和启动超时后再次可用。
4. 正文长度和关键词只能辅助检查，不能代替行为验证。不给 memory 增加任意 1500 字符警告。

## 6. 实施顺序

1. 保存现有失败基线，逐项复核旧执行计划，区分代码、离线验证、现场证据和能力缺口。
2. 对已复现缺陷先加失败回归，再修输入/焦点/读回、启动/桌面恢复、卸载与未知版本召回。
3. 修正工具参考与实现的差异，再加强 skill 的操作卡、调用示例、结果分流、恢复和结束条件。
4. 用实际 schema 和独立操作者情境验证文档，不以禁止数字或压缩行数代替指导质量。
5. 跑全部离线测试与差异检查；GUI 自检、HTTP 服务和真实应用验证另列为未执行，直到取得当轮证据。

每一步都要能独立回退：改测试、搬文档、瘦身正文是三件事，不要合成一个提交。

## 7. 不做的事

- 不改 `memory.py` 的存储格式与 schema（当前格式够用，问题在写入粒度）。
- 不给 MCP 加"自动查记忆"的能力（跨版本误配风险大于收益）。
- 保留 `foreground-protection.md` 的实现与验收细节，只纠正已过期的 MCP 桌面入口表述。
- 不把 `docs/reports/` 的历史报告删除或合并（它们是原始证据，只增不改）。

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 瘦身时误删原则 | 方法缺失 | 先把方法条款列成清单，逐条核对再删 |

## 9. 验收标准

- skill 的常见路线均能回答触发、调用参数来源、预期、验证、失败转向与停止/恢复条件。
- 工具参考与当前实现一致，示例经实际 schema 校验，不发明 offset、工具、隔离或跨版本保证。
- 已复现缺陷的行为回归先红后绿，全套离线测试不回归；当前未提交文档的测试冲突已解决。
- 真实记忆不因文档整理被删改；未知版本观察缺失不回退到其他版本的高信任路线。
- 真实 GUI、已安装 HTTP 服务及应用兼容性只按当轮保存的结果验收，不预写“54/0”“13/0”。
