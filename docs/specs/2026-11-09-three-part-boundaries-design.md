## 1. 三部分的职责（单一归属原则）

每个事实只能有一个**权威归属**，其余地方只能引用，不能复制。

| 部分 | 只负责 | 明确不负责 |
|---|---|---|
| **skill** | 方法：路线顺序、调用前保护、如何验证、何时降级、如何留证据 | 不写任何具体应用的实测数字、控件名、版本结论 |
| **memory** | 结论：某应用某版本，某条路线**是否可用**，以及可信度 | 不存原始证据、不存测量过程、不存大段报告 |
| **MCP** | 执行与读回：把动作可靠地做出来，并如实报告"做了什么/没做什么" | 不判断业务语义、不替调用方决定该信哪条路线 |

一句话：**skill 说"怎么做"，memory 说"这个应用能不能这么办"，MCP 说"这次办了没"**。

## 2. skill：方法只留原则

### 2.1 保留（原则与判断流程）

- 四级路线顺序（后台高效 → 后台低效 → 前台高效 → 前台低效）及降级理由要求
- 调用前防抢焦的验收条件、失效判定、退出条件
- 基础探测：区分"未试 / 权限不足 / 工具缺失 / provider 报错 / 执行了但没效果"
- 效果验证原则：返回值、元素数、像素、业务标志各自能证明什么
- 任务范围与路线台账的字段要求
- 写 memory 的规则（正文八节、保留失败与未试方向）

### 2.2 移出（不许留在 skill 正文）

| 内容 | 现位置 | 移到 |
|---|---|---|
| QQ / 微信具体数字与控件名 | 「按界面与任务选择路线」等 | 对应 `docs/reports/`，skill 只留一句"见报告" |
| 启动 flag 对照表（13/315 等） | 「启动条件对照」 | 报告；skill 只留"空树先查无障碍 flag"这条原则 |
| `msg` 数值与 `invoke_pattern` 参数 JSON | 「调用小抄」 | **工具文档**（README 或 `deskweft/server.py` 的 docstring），skill 不再复述 |
| `find_items` 的字段与边界 | 「ItemContainer 专用查询」 | 工具文档；skill 只留"末页不等于全量"这条判断 |
| 历史起点转录（9/128/132 等） | 「随 skill 携带的历史起点」 | 删除或并入报告附录；它不是方法 |

### 2.3 拆分后的结构

## 3. memory：按路线拆，一条一个结论

### 3.1 颗粒度

一条 plan = **一个可判断的结论**，形如"在 QQ 9.9.37 上，搜索框 `SetValue` 可用"。
不再有"整轮探测"这种 plan。

### 3.2 正文形态

八节标题对"路线"仍然成立，但每节只写这条结论需要的最小内容：

```text
## 目标        这条路线要达成什么（一句话）
## 环境与适用条件  应用版本、窗口状态、启动条件
## 已验证步骤    编号步骤，每步写调用与预期
## 已尝试但失败  本路线实测失败的条件（没有就写"本路线未出现失败"）
## 实测记录      完整成本、覆盖率、副作用证据（指向仓库证据文件）
## 未解决       本路线仍不确定的部分
## 未试方向      本路线尚未覆盖的变体
## 更新记录      何时由谁验证/推翻
```

### 3.3 与应用实测的分工

- memory 存**结论与指路**：哪条有效、哪条无效、证据在仓库哪个文件。
- 原始 JSON、截图、脚本一律进仓库（`.superpowers/sdd/<日期>-<主题>/`
  或 `docs/reports/` 的附件目录），并在 plan 的「实测记录」里给出路径。
- memory 里不允许出现"完整测量过程"，那是报告的事。

## 4. MCP：可靠性的表达方式

工具不承诺"这个动作一定生效"，改为**如实分级报告**。三级：

| 级别 | 含义 | 现有字段 |
|---|---|---|
| 执行结果 | 调用到没到、provider 报没报错 | `ok` / `reason` / `execution_state` |
| 效果证据 | 有没有观察到界面真的变了 | `observation` / `route_effect` / 读回值 |
| 路线可信度 | 这条路线在该应用上被验证过几次 | **当前缺失** |

第三级是本轮要补的：memory 里有路线结论，但工具返回时不会带出来。
设计上**不自动推断**（自动匹配 memory 容易把旧版本结论套到新版本），
而是让调用方显式查（`recall`）后自己判断。MCP 侧只做一件事：
**保证前两级不说谎**，即凡是"不知道有没有生效"的，必须报告为未知，不能报成功。

### 4.1 已知缺口（不在本轮修，但要在文档里承认）

- `invoke_pattern` 无法传 Control 引用，ItemContainer 的续项只能靠 `find_items`
- Chromium 上 `ScrollPattern` 不可用，`find_items` 对虚拟列表可能只看到已渲染部分
- 同一 API 在同一窗口内有的控件执行、有的不执行（导航按钮 vs 搜索行），
  工具无法在调用前判断

这三条写进 `references/tool-reference.md` 的"已知缺口"，不写进 SKILL.md。

## 5. 怎么防止再次混淆

用测试而不是靠自觉。但这里有一个**必须先解决的冲突**：

### 5.1 现有测试正在反向锁死

`tests/test_skill.py` 里有几条断言，**要求** skill 正文包含具体数字，与
"§2.2 移出具体数字"直接冲突：

| 测试 | 断言 | 冲突 |
|---|---|---|
| `test_historical_numbers_are_marked_historical` | `assertIn("132")`、`assertIn("128")` | 要求正文保留历史节点数 |
| `test_untried_directions_survive` | 必须出现三个 `--disable-*` flag 名 | flag 名属于工具/启动文档，非方法 |
| `test_covers_every_surface` | 必须出现 UWP、Electron 等 | 可保留（属方法层面的界面分类） |
| `test_all_shipped_resources_are_reachable_inside_the_skill` | skill 目录下所有文件都必须被 md 链接到 | 新增 `references/tool-reference.md` 时必须同时加链接，否则失败 |
| `test_new_tool_names_are_the_real_ones` | 必须出现 7 个工具名 | 若工具手册移出，这条要改成指向 tool-reference |

**处置**：瘦身时同步改这些测试，而不是为了迁就测试把数字留在正文。
改法：

- `test_historical_numbers_are_marked_historical` → 改为断言"历史数字**不在**
  SKILL.md，且出现在某份报告里"（反向断言）。
- `test_untried_directions_survive` → 改为断言"三个方向在 skill 或
  tool-reference 之一出现"，不限定 SKILL.md。
- `test_new_tool_names_are_the_real_ones` → 指向 `references/tool-reference.md`。

这一条要先做，否则第 2 步瘦身会立刻撞红一片。

### 5.2 新增的约束测试

1. `SKILL.md` 不得出现 `9\.9\.\d`、`\d+ px`、`\d{3,} 元素` 这类模式；
   出现即失败，并提示"这属于报告或工具文档"。
2. 单条 plan 的 `body` 超过 1500 字符时给出警告字段，提示应拆成多条或
   把过程移出 memory。
3. 每份 `docs/reports/*.md` 必须能被 README 或某份 spec 引用到，
   避免报告成为孤儿。

## 7. 不做的事

- 不改 `memory.py` 的存储格式与 schema（当前格式够用，问题在写入粒度）。
- 不给 MCP 加"自动查记忆"的能力（跨版本误配风险大于收益）。
- 不重写 `foreground-protection.md`（它是独立的保护契约，已经够清楚）。
- 不把 `docs/reports/` 的历史报告删除或合并（它们是原始证据，只增不改）。
