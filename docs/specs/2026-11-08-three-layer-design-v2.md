# DeskWeft 三层框架：设计与依据

审核修订：2026-11-08。基础三层实现已落地；本轮修补结构化目标、后台只读属性、专用 ItemContainer 查询和 skill 的具体探索路线与完成标准，不推断历史设计审批结果。下文基线缺陷与现场观测保留为设计依据，不表示它们仍未修复或本轮重新实测；本轮真实 provider 测试另存独立报告。
本文件取代 `2026-11-08-three-layer-design.md`，只解释决定的理由与证据边界。
**签名、字段、文件格式、skill 正文与验收只在 [implementation-handoff](2026-11-08-implementation-handoff.md) 维护。**

项目现名为DeskWeft（Python包/CLI：`deskweft`）。改名更新当前入口与部署路径，旧现场命令、产品标识和源码哈希仍是历史证据；名称变化不证明旧GUI任务已复验，新的离线、部署与客户端配置验收见交接稿§0.1，现有运行中会话的重载范围另行说明。

## 1. 要解决的问题

改名前的基线 winmcp 有 8 个按窗口寻址的工具。QQ 的探索结果已经写进 `server.py` 的 INSTRUCTIONS 和 README，因此当时的问题不是“没有记录”，而是记录不能按软件与版本查询，也没有区分已验证路线、候选假设和现场限制。

框架目标是 **skill 支持面广、memory 记录清晰、MCP 执行可靠**：skill 要能指导不同 Windows 软件的发现、诊断、探索和效果验证，而不是只复现 QQ 的成功路径；memory 要能区分已证实有效、已试失败、尚未尝试及其环境条件；MCP 要把可执行能力、权限、失败和可观测效果说清楚。

这样才能减少重复探索，同时避免把某台机器、某版本、某次成功误当成通用事实。面向一位用户的本机服务，不为多租户或多机同步设计；这个部署边界不缩小 skill 面向不同软件和失败情形的探索目标。

## 2. 三层分工

```text
skill    覆盖不同软件的探索与验证方法，包含失败分支和未试方向
  ↓
memory   按 app@version 保存有效路线、失败、未试方向及环境与证据
  ↓
mcp      可靠读取与执行，报告权限、能力限制、失败和可观测结果
```

skill 规定如何查阅已知路线、失败和未试方向，以及何时继续探索；具体软件知识由 memory 持续积累，不因 skill 保持静态而丢弃。memory 不提供自动执行权限；MCP 不根据历史记忆跳过当前调用的权限检查。一次探索得到的结论和失败路径连同版本、窗口状态、参数及证据进 memory，下次按条件召回；已确认的能力缺口成为工具演进的依据。

基础实施新增 7 个工具：3 个身份/执行入口（app_info、invoke_pattern、post_message），2 个记忆入口（recall、remember），2 个独立审核入口（approve、confirm_proven）。连同原有 8 个共 15 个，再加一个静态 skill；本轮另补专用 find_items 后为 **16 个工具**。本轮保持既有入口、memory 格式及信任边界；可靠性修正不能被替换成延后能力、删去失败分支或缩小 skill 支持面的理由。

## 3. 记忆为什么这样存

### 3.1 按 app 与完整版本组织

应用无障碍行为、启动 flags 和控件结构会随版本变化，因此需要版本边界。版本不是随便截取的短标签：原稿自身记录了 FileVersion 与 QQ 安装目录不一致，截成 `9.9` 会进一步丢失信息。

目录中存在某个版本，不代表当前进程运行该版本。版本证据必须跟随实际 exe 路径；不能从多个安装目录挑最大的一个。来源不确定就暴露不确定性：完整 FileVersion、候选目录或未知值，比错误的精确 key 更有用。

找不到精确 key 时仍可返回同 app 的历史版本，但它们只是探索候选。`exact` 表示记录匹配，不能代表程序行为已经验证。

未知版本不应阻止保存本次探索。用 `version=None` 对应 `app@unversioned` 保存未定版本观察，明确记录当时的 exe、环境、失败与未试方向；这不是伪造一个发布版本。该记录的有效 reviewed/proven 始终为 false、rank 始终为 0，不得审核或确认为已证明。以后确认实际版本时另建本版本记录，保留来源再独立验证，不能直接把应用级观察升级成某一版本的结论。

### 3.2 一个 key 一文件，正文内嵌

同一版本可有只读、前台操作等多条方案。把它们放在同一记录内，保留各自的代价和验证标签，避免把取舍压成一个“最佳方案”。

保留 Markdown 文件和 YAML frontmatter；将每个方案的 Markdown 正文内嵌为多行字符串，删除独立正文文件与索引。这样一次原子替换即可提交整条记录，不再需要处理“索引已更新但正文没写完”、正文路径穿越或孤儿文件。

采用成熟的 safe_load 和显式 PyYAML 依赖。手写 YAML 子集需要处理转义、类型、缩进及错误恢复，代码与风险都高于这一个直接依赖；当前 venv 偶然装有 yaml 不构成安装契约。

文件名由 key 的稳定摘要生成，保留原名作为内容。将非法字符替换成下划线会让不同中文应用共用路径；直接拼用户字符串也难以正确处理 Windows 文件名规则。

### 3.3 本地存储与并发边界

memory按`DESKWEFT_MEMORY_DIR`→兼容`WINMCP_MEMORY_DIR`→`%LOCALAPPDATA%\winmcp\memory`取根目录。保留旧默认路径可继续读既有知识，不因产品改名迁移或重写正文、revision与信任位。

memory 存放在本机用户数据目录，不进代码仓库。软件路径、版本及用户设置属于现场信息，跟随代码发布会制造错误的确定性。

预期规模下扫描文件即可，不需要数据库、索引缓存或目录分页。正文有整次响应预算，防止按软件名一次召回多个版本时无限灌入正文；元数据仍随本机记录数量增长，规模明显增大后再加目录分页。

传输有预算不代表知识永久不可读。`recall` 支持通过 `plan_id/body_offset` 续读单条正文，按返回的下一偏移读完；每片核对同一 `revision`，内容变更就丢弃旧片段重新读取，避免把两个版本的步骤拼成一条方案。只有读全且修订一致才可按完整步骤执行。这是单条正文的传输能力，与整个目录的分页无关；具体偏移和返回契约由交接稿统一定义。

`os.replace` 只保证整文件替换，不保护“读旧记录、追加方案、写回”的竞争。因此用一个进程内锁覆盖完整写事务；这足够支撑当前单服务的并发会话。明确不承诺多个进程或外部编辑器同时写同一目录，避免为了未出现的需求先做锁服务。

## 4. 可信度为什么分开

### 4.1 reviewed 与 proven 是两件事

`reviewed` 表示用户看过并认可方案，`proven` 表示有多次真实成功记录。它们不能合并成一个“verified”，也不需要为 blocked、needs-tool 等再建状态机。

排序为 `rank = 2*proven + reviewed`，即 3、2、1、0。它表示优先查看哪条经验，不表示自动执行哪条操作。`reviewed=true, proven=false` 也不能推断一定成功过一次；人的认可不是运行证据。

新方案默认两位都为 false。覆盖步骤、代价或副作用说明后清零被改方案的验证位，否则旧步骤的审核会被转嫁给新步骤。审核还须比对用户看到的内容摘要，阻止另一会话覆盖后将旧确认授给新内容。审核与实战确认独立操作并可撤销；本轮由用户确认，不加自动计数。

### 4.2 先过滤副作用，再看排名

`cost` 是供人比较的文字，不能可靠承担“用户正在工作时是否能执行”的判断。因此保留单独且必填的 `uses_foreground`，未知时按 true 处理。

用户正在操作电脑时，先排除需要前台的方案，再排序。用户离开也不等于给出了业务操作或重启授权。rank 高只减少重复探路，不能取消当前目标效果验证或工具的权限门。

rank 衡量经验可信度，不能表示路线效率。已有高 rank 路线可作为基线，仍须核对用户要的是当前项还是完整数据、是否满足后台约束，以及定位、调用、验证的整条成本。具体 selector 仍要检查当前树，不能只因参数更精确便声称速度更快；查询一个名称与采集全名单的成本也不能直接比较。本轮要求保存可比任务范围、样本、调用/全树读取次数与副作用证据，没有测量的指标保持未测。

同样，返回 `foreground_changed=false` 只是前后观测，不是防止夺焦的措施：provider 可以中途切走再切回，异步消息还可能在工具返回后改变状态。授权必须在动作前判断。

### 4.3 跨版本只共享步骤，不继承验证

`see:key` 保留跨版本复用，但只跟随一次，作为候选方案返回。源版本的 proven/reviewed 不能证明目标版本也成功；派生结果的有效 rank 为 0。

目标版本要独立验证时，将继承内容显式落成本版本记录，再审核。这样不用再引入一套独立的“继承状态”，也不会因为源文件后来修改而把旧审核无声套到新步骤上。

### 4.4 缺口从真实正文派生

探索失败和未试方向写入各 plan.body 的“未解决”段落，召回和缺口扫描读取同一正文。删掉该段即关闭缺口，不再维护 gaps.json、needs-tool 字段和独立关闭状态。

这也修正原稿的断链：写工具把未解决内容写到 plans 文件，扫描器却只看 playbooks 文件，结果真实记录的缺口永远查不到。

## 5. 身份、通用执行与专用查询入口的取舍

### 5.1 app_info：给出身份和来源

现有 windows 只提供 pid、标题、类等元数据，无法支持版本查询。单独的身份工具补上这一步，同时保留来源与未知状态，避免让 skill 先猜版本才调用 recall。

不把 QQ 的目录布局写成全软件通用版本规则。实际路径能证明活动目录时才采信；其他来源完整返回。具体应用的安装器异常留在该应用记忆里。

### 5.2 invoke_pattern：扩大 UIA 探索能力，完整返回可用结果

现有动作路由只覆盖常见操作。通用入口要让 skill 既能执行其他 pattern 方法，也能读取公共属性链和方法返回的状态、文本与结构化结果；不能因为值不是简单标量就丢弃，也不能用“工具拒绝了”代替可靠实现。如果探索得到了 TextRange 或 Control，却既不能读取也拿不到可用投影，skill 仍会在关键处断路。

依赖封装与 provider 支持是两个不同条件：`GetPattern` 存在不代表接收字符串，也不代表依赖实现了所有模式。先复用已有 wrapper；遇到枚举存在但 wrapper 缺失时，明确记录所需适配、可验证的接口和当前限制，补齐框架需要的封装，而不是把依赖当前覆盖面当成长期能力上限。确实未实现的接口仍应如实报缺口，不能假装可调用。

普通结果转为 JSON；已知 Control、TextRange 等结果由实现读取并投影成可用的文本、属性或结构快照。原始 COM 对象不外泄、不跨线程缓存；未知对象清楚报告尚缺哪种投影。公共属性链和显式方法提供可理解的探索面，不开放任意表达式执行或私有成员访问。准确的调用和投影契约只在交接稿维护。

读取属性与可能改状态的方法需要区分：明确只读白名单按完整成员路径允许后台查询，不凭 Get 前缀猜测安全；写入和未知成员可能夺焦、关闭窗口或修改数据，仍须相应授权。白名单 provider 也可能实现有误，因此查询同样受预算和副作用观测约束，出现反例要保留该应用的环境记录。要求显式方法及参数，不猜默认方法，不在失败后自动换鼠标路线。

目标必须精确且唯一，拒绝模糊命中与不完整树中的不确定定位。通用出口比日常点击更容易表达危险动作，不能复用“取第一个近似名称”的便利行为。

本轮补齐组合 selector，让同名或重复 AutomationId 的控件可以用当前控件类型、真实 native HWND 和附加矩形共同消歧。各字段必须同时精确满足，矩形不能独立定位，元数据读取不全也不能默认排除潜在候选。它保留原字符串调用的兼容性，扩大可以可靠表达的目标；不引入首项/索引选择、最近坐标猜测或缓存 COM 元素。结构化 click/type 在完整解析后，仍可利用核对过的原生 child 和既有允许类走后台消息，其余路线保持权限门。具体字段、校验和拒绝顺序只在交接稿 §4.5.1 维护。

可靠的唯一性还依赖候选集合完整。匿名节点即使没有常用七项 pattern，仍可能满足类型/句柄/矩形条件，本轮保留所有可读非 offscreen 节点；七项摘要只描述常见能力，不能作为删节点的理由。只剩一个已命名节点并不证明原来只有一个同类目标。服务也须保留 worker 动作前后的真实前台采样，缺失时才补整个调用前后观察；动作完成后重新取两次相同样本会掩盖刚发生的夺焦，破坏 memory 副作用证据。

保留更多节点可能更早耗尽元素预算，届时报告不完整并拒绝，不能为了继续动作恢复匿名过滤。selector 提高可表达的精确性，不承诺减少树遍历或自动提速；这些代价必须进入路线的完整成本比较。

后台只读能力也应覆盖依赖实际实现的公共状态读取。本轮按 windows-mcp 0.8.8 wrapper 核对并扩充显式完整路径表，包括 Legacy Name/Description/Value、WindowVisualState、Grid 计数及其他已核验 scalar getter；不能把这些读操作长期挡在与写操作相同的授权门后。该扩展不按 Get 前缀开放方法，不放行 Legacy 默认动作、Window 修改方法或原始 COM 导航，也不证明 provider 不会夺焦。精确表、投影和拒绝测试仍由交接稿 §4.3 统一维护。

通用 args 不接受列表内 null 或 Control 引用，返回的 Control 元数据也不是持久句柄；这曾使 `ItemContainerPattern.FindItemByProperty` 的首轮 NULL 起点与引用续项均无法表达，不能由此判断应用没有暴露该模式。本轮用 §5.4 的专用 find_items 托管这一个受控查询，不为通用入口开放任意原始 COM/指针或跨调用引用；其他方法需要 Control 输入时仍明确报告适配缺口。

这条可靠定位原则也适用于既有 `click`：原生未命中可继续尝试已授权的 UIA 路线；原生或 UIA 存在歧义、UIA 读取不完整、最终仍未找到命名目标时必须拒绝，不能退回点窗口中心。控件消失或没读全是定位失败，不是授权服务点击另一个位置；公开签名可以保持不变，纠正内部回退行为才能避免把任务失败变成误操作。

诊断必须保留异常来源，区分依赖未封装、provider 未暴露、成员访问异常、COM 错误及预算耗尽。守卫返回 None 只表示这次没有取得可用对象，不能直接解释成“应用未暴露此 pattern”。在吞掉异常或返回兼容值之前保留出错阶段、异常类型与可用错误码，才能让 skill 选择补封装、换定位、调整读取或保留失败证据，而不是错误关闭一整条探索路线。

UIA 对象还有线程边界。同步 MCP 可能在线程池运行，读取、取 pattern 与调用必须处于同一个已初始化线程；主线程直调成功不足以证明服务调用正确。

provider 调用还可能无限阻塞，Python 遍历预算或线程 future 超时都不能终止卡住的 COM 调用。因此将读取、动作和通用调用放进一个可重建的 UIA worker 进程，串行执行并在该进程内初始化 UIA、立即投影为普通数据；服务监控等待期限，只终止和回收自己创建的失去响应的 worker，避免阻塞耗尽 HTTP 线程。终止 worker 不等于取消目标应用已收到的动作：超时结果统一标为 `execution_state="unknown"`，先核对目标状态，不自动重试。动作执行前拒绝和已执行后验证失败也要分别表达，不能都说成“什么也没发生”。进程边界是为了可靠保留能力，不是把异常 provider 排除在探索范围外。

### 5.3 post_message：支持有界同步与托管文本，区分处理结果

原生消息不仅用于投递点击，也用于查询状态、读取和设置文本。入口保留异步投递，也恢复有界同步等待：异步使用 PostMessageW，等待处理结果使用 SendMessageTimeoutW，不能用无界 SendMessageW 让目标应用卡住服务。保留同一个工具名，避免让 skill 在另一个缺失工具前停下。

WM_GETTEXT/WM_SETTEXT 等常用文本消息由实现分配、管理缓冲区并返回文本或处理结果，不能要求 agent 从 JSON 构造进程指针。其他需要指针、句柄或专用封送的消息，必须有对应的托管实现才可支持；明确报告尚缺的能力，不把不支持缓冲区作为删除所有同步查询的理由。

异步成功只报告 queued，同步处理返回报告 returned；两者都不等于业务目标已经完成，skill 仍须读回验证。同步超时不表示目标已取消处理，结果统一以 `execution_state="unknown"` 表达不确定性；不自动重试写入或点击，托管缓冲区也必须在超时后保持安全的生命周期。这些是可靠执行必须承担的实现责任，不通过丢结果或删掉 wait 回避。

“已知整数参数”不等于“无害”：发送字符、点击或未知消息都可能产生业务和前台副作用。编号放行、数据形态、前台授权分别判断；广播和原始指针不开放，受支持的文本消息则走托管路径。具体参数、等待预算和结果字段只在交接稿定义。

### 5.4 find_items：把 ItemContainer 的引用留在一次查询内

ItemContainer 的 NULL 起点与元素续项是同一固定接口的内部状态。为它增加专用有界查询，比让客户端持有任意 Control/COM 引用更直接：worker 重新定位容器、枚举和投影，调用结束即丢弃引用；协议只接收属性值和匹配偏移，不新增跨调用元素缓存。它也保留虚拟化项目的可读元数据，不要求先 Realize、滚动或夺焦，避免将“当前可见树只有少数行”误当成数据只剩这些行。

分页是实时重扫而非快照，每页从 NULL 走过此前匹配项，因此后页成本会包含前缀。UIA 不保证稳定顺序，虚拟 peer 的 RuntimeId 也可能跨调用改变；RuntimeId 用于本次循环检测，不能充当稳定业务键。provider 返回 NULL 只证明该匹配序列到尾，仍可能跳过相等业务项；独立总量、经核验的业务身份和重叠页一致性才支持更强覆盖结论。

保留 max_items=100、总文本预算、worker期限与字段错误，不为全量目标取消边界。complete 仅在首偏移从0、provider到尾且元数据无错误/截断时成立，后页 reached_end 或多页拼接不自动提供业务全量保证。离屏属性报错时仍返回其他已读字段和诊断，不能假报“完整元数据”，也不能为了得到干净结果自动改变应用状态。详细签名、字段与失败分支由交接稿 §4.7 维护；真实测试、被证伪假设及环境见 [本轮 ItemContainer 报告](../reports/2026-11-08-itemcontainer-live.md)。

2026-11-08 独立实测以进程内 MCP 客户端、真实 worker 和 Windows provider，核对了 WPF 的300项合成数据（12个重名）与 Explorer 的150个空文件；重叠页均与独立清单相符。WPF 部分 IsOffscreen 读取失败但名单字段保留，且跨调用观测到2次 RuntimeId 变化；Explorer 的元数据完整。未测试 HTTP 或重启已安装服务，前台两点采样不构成全过程无夺焦证明；具体环境、原始记录及限制见上述报告，不能并入下文旧现场数字。

## 6. skill 如何覆盖更广的软件与探索方向

### 6.1 稳定流程覆盖成功与失败分支

skill 负责辨识目标、召回、过滤权限、读取、验证效果及回写；应覆盖原生控件与窗口消息、UIA 的方法/属性/文本、Chromium/Electron 无障碍条件、UWP 的窗口与内容定位、自绘界面的视觉验证、虚拟化列表的分段读取等不同切入点。还应考虑应用提供的官方 API、CLI 或其他可用接口，避免把所有目标硬塞进同一条点击路线。覆盖广意味着遇到新软件或失败路径仍有可执行的诊断方法，不意味着预先承诺每个 provider 都支持同一操作。空树可能由超时、过滤、隐藏状态、错误窗口或未开启无障碍造成，不应立即诊断为 Electron。

官方 API、CLI 或专门读取工具属于可选路线，先确认环境中是否存在、任务是否授权及输出能否验证；尚不存在的工具写成明确能力缺口，不能假装当前 MCP 已实现。MCP 应可靠承担本轮七个入口应有的读取、结果投影、同步等待和执行能力；skill 的思路范围则不被这七个名字限定。

未知版本仍通过未定版本观察保存探索成果；截断正文先按 revision 一致性续读完整再使用。定位失败、权限未满足、能力缺口、provider 异常与已完成但效果未达成分别记录；不能把 None、空树、queued 或超时当成对应用能力和动作结果的最终证明。

重调 open_app 不会自动重启已有实例，单实例应用也可能忽略传给新进程的 flags。把“检查启动条件”与“实际重启并保护用户工作”分清，比硬编码更多重试更重要。

启动可靠性还要求有窗口归属证据。现有 launch 会隐藏观察期内所有新窗口，可能碰到无关应用；交接稿要求按实际启动进程及已核验子孙筛选，两个隐藏循环共用判断。单实例转交或broker归属无法证明时保留启动与后续定位能力，明确报告未确认，不凭标题或相同exe隐藏已有窗口，也不争抢用户主动切换到的其他应用。

截图能够描述可见内容，不能证明虚拟化列表完整。skill 要求查阅并保留 memory 中的未试方向，不能把“当前工具没成功”写成“没有其他路径”。具体应用的 GPU 参数猜想、实验代价和结果进 memory；静态 skill 维护探索方法，动态知识随 memory 积累。技能正文和具体调用规则只在交接稿维护。

### 6.2 必须保留的未试方向

以下来自基线原设计稿 §5 和原交接稿 §7.2，**均为待探索假设，本次未验证，不能当作已有效方案**。它们解释为什么框架需要保存“还没走过的路”，不是要求 agent 不经判断立即执行。

| 未试方向 | 原稿希望验证的问题 | 代价与边界 |
|---|---|---|
| 滚轮或 ScrollPattern 失败后试 `--disable-gpu`，观察禁用 GPU / 软件渲染路线 | 渲染方式是否影响 QQ 等应用的滚动或后台可读性 | 原稿提示可能明显降低性能；是否改变该应用行为未知。修改启动参数通常需要新进程，先确认性能代价和重启授权，保护用户工作 |
| 尝试其他 `--disable-features` 组合，包括关闭 GPU 合成的方向 | 已用防遮挡组合之外，是否还有影响后台渲染、读树或滚动的特性 | 原稿未给出已验证的具体组合；不能编造可用 feature 名或承诺有效。记录实际参数，分别对照效果和性能，重启前确认授权 |
| 后台读树失败时，不带 `--force-renderer-accessibility` 裸启动作对照 | 区分该应用默认行为、无障碍 flag 与其他启动条件的影响 | 可能得到更少控件，不能预先当成修复。与带 flag 的样本保持可比条件，记录其余参数；不自动关闭现有实例，按重启权限处理 |

每次实验都把实际版本、窗口状态、启动参数、观测和是否验证写回 memory；有效路线、已试失败和仍未尝试应能直接分辨。失败证据和未试方向同样有价值，不能为了缩短文档或提高方案排名而删除。

### 6.3 本轮修补：把候选变成可执行的探索路线

只要求“不要过早停止”不足以帮助陌生软件的探索。skill 应在已观测的界面上给出触发条件、实际操作、结果/完整性验证以及权限或工具缺口，才知道下一步能怎样推进。交接稿 §6.1 随源码同步完整规则；以下说明必须保持的探索面及其依据：

| 当前观测或任务 | 有根据的操作方向 | 必须核对的证据与边界 |
|---|---|---|
| 已发现原生 child | 以实际 child HWND 用托管 WM_GETTEXT 或允许的状态消息读取 | 保存文本/状态与来源；确属目标窗口且类适用；不传客户端指针 |
| 内容确由根窗口暴露 | 用 invoke_pattern 的显式空字符串 target 直接读取根 pattern | 先证实根承载目标；可避开一次目标树查找，但仍测定位+调用+验证总成本 |
| Value 为空、读回不可用或同一目标存在多种语义 | 比较 Value、Text、Legacy Name/Description/Value 等当前允许的读取 | None、空串和截断分别记录；交叉结果须对应同一业务字段，不编造完整值 |
| 需要计数、选中项或列表边界 | 读取 Selection、Grid 计数、Scroll 位置或其他已核验状态 | 选中项不等于全量，Grid 总数不等于已经取得所有项目；GetItem 等成员按实际白名单与授权 |
| 重名导致无法安全定位 | 按完整当前树使用组合 selector 消歧 | 全部谓词一致且唯一；字段变化时重新观察，不能删条件重放动作 |
| 长列表滚动无进展 | 核对容器，调查搜索、筛选、分页、展开、Text/Selection、分段导出；ItemContainer 使用 find_items，VirtualizedItem 按实际封装/授权探测 | 单次无进展只结束该循环；分页重扫、字段错误、provider序列与业务总量分别核对，不能只凭末页声称全量 |
| UI 成本高或需要精确完整数据 | 调查应用导出、已有官方 API/CLI、合法浏览器语义接口与本地输出 | 确认工具确实存在、任务授权、字段和总量；可用接口的提议不能冒充 DeskWeft 内置能力 |
| UWP 壳空或内容宿主不同 | 调查实际 CoreWindow/内容 HWND，并重新读取 | 核验进程/窗口身份；壳为空不能关闭整条 UIA 路线 |
| Electron 后台树消失 | 以实际启动参数和窗口状态做单变量无障碍/遮挡对照 | 重启和 GPU 对照保留原授权与性能边界；未试假设不升级为已有效路线 |
| wrapper 缺失、属性投影或 Control 输入不可表达 | 记录具体缺口和可核验的后续适配方向 | 与 provider 未暴露区分，保留已得到的结果；不突破原始 COM 和参数边界 |

以已有可用路线为基线，维护候选台账：适用依据、已验证/失败/未试/权限阻塞/工具缺口/不适用状态、覆盖范围、完整成本、前台/鼠标证据、下一步或本次未试原因。对已发现、适用、低成本、已获授权，且能推进目标或用户要求效率的候选实际验证；不能仅列“未试”便结束。对其余候选给出可核实的原因，不要求技术穷举、固定次数试验或宣称全局最优。

结束条件依用户目标而定：取得部分名单只支持 partial，不能以此结束尚可继续的全量任务；一次空树、滚动不变、某方法缺权限只限制相应路线。先继续当前许可内有根据的独立调查，确实受阻时说明每条剩余相关方向的具体限制与所需条件。任何 queued/unknown 副作用都先查清执行状态，不因“换路线”或比较效率而重放同一点击、翻页、提交或写入。现有历史 GPU/裸启动等假设和失败证据全部继续保留。

### 6.4 QQ / 微信当前实测：后台可读、动作有效与无夺焦必须分开

2026-11-08 新实测另存 [QQ/微信报告](../reports/2026-11-08-qq-wechat-live.md)，不回填下文历史表。QQ 活动版本由 child_cmdline 得9.9.22（renderer app-path为9.9.22-40824），FileVersion仍9.9.19.35469；实际退出旧进程并以三项无障碍/防遮挡参数启动新进程后，从已显示旧实例8个无命名外壳元素读到新主窗口312元素、128命名。这是当前环境/启动条件的证据，不把多个同时改变的条件冒充单参数因果对照。

后台Legacy联系人/消息导航四轮有效，每轮定位与动作请求再加独立see验证为3009.2–3607.0ms；只能报告端点未见前台变化，不能用单个动作的969.6ms替代完整成本或宣称全程无夺焦。搜索ValuePattern.SetValue则确实生效并把前台从微信切到QQ，稳定selector的后续实验已验证恢复原值。QQ几个实际容器的ItemContainer获取返回pattern unavailable/cause_unknown，不能断言整个应用不支持或完整名单已取得。

上述导航样本没有验证有效的调用前防抢焦保护，不能按当前强化门槛登记为已验证合格后台路线；它们保留为导航功能与采样端点的事实。保护新变体与原路线分开计证，不从动作有效或历史rank继承后台保证。

失败的防护试验进一步说明事后观察不等于调用前保护：LockSetForegroundWindow未取得（error5），禁用已知顶层仍捕获QQ窗口的前台事件，写入报provider error且原值未变，最后恢复了窗口enabled状态。工具allow_foreground授权只允许执行，不提供防夺焦机制；已知抢焦路线不进入后台候选，没有可靠防护就保留缺口并推进其他只读调查。前台实验授权不会把它改造成后台方法，也不改变后台高效→后台低效→前台高效→前台低效的推进顺序；同层在相同范围比较定位、调用、验证的总成本。

保护自身也必须有可核验的契约，而非另一个未经证实的开关：范围覆盖具体进程/renderer、worker和必要session/desktop；在进入provider前检查生效约束，失效时停止动作，退出时不放行尚未完成的异步处理。queued、超时、固定等待或一次状态不变不能证明处理终止，前台事件观测也不能替代阻止机制。保护建立/验证、一次性准备、worker/调用/等待、效果验证和撤销/恢复均计入闭环成本；缺少安全退出或完成/可靠取消证据时保留执行未知与工具缺口。后台低效仍先于前台高效，成本未测不能被猜成低效而跳过；已满足目标则无需继续执行更低层。

非输入desktop试验另按轮次保存：首轮因真实worker身份核验失败停止，未进入setter；第二轮worker自报与29个QQ根/renderer HWND归属核验通过，先执行Legacy语义focus，再完成搜索写入、独立读回与精确恢复。第二轮12个已计时请求合32673.6ms，但保护建立/归属检查/清理未全部单列，不能作为完整端到端成本；父端input desktop采样保持Default，前台端点却有Explorer变化与未归属事件，不能声称整个用户前台从未改变，Job handle关闭也不单独证明活动进程归零。

后续随skill交付私有desktop/Job控制器、真实dispatch线程逐调用保护与QQ语义runner。审阅发现的unknown后恢复重写、清理异常覆盖根因分支已修复并作离线验证；旧登录通用click可能退回真实鼠标，旧日志未保留路由，因此也改为显式Legacy.DoDefaultAction，禁止fallback。当前入口整轮实跑已完成显式语义登录、不先搜索focus的直接SetValue、独立Value读回和精确恢复，实际worker和31个QQ根/renderer HWND归属核验通过，Job实查ActiveProcesses=0。11请求30370.0ms，包含保护建立、启动/登录等待、恢复和清理的helper生命周期35660.522ms；576个输入样本保持`1/WinSta0/Default`，但用户desktop有33条事件（Explorer19、DeepSeek Harness9、Terminal5），不能从端点相同声称全程未变。旧34秒轮次及23条事件仍在报告保留，不倒填为新登录入口的证据。该能力只适用于已核验留在非输入desktop的普通窗口激活路径，不是阻止同权限显式切桌面或外部broker的安全沙箱；新实例、renderer/worker、session及版本条件变更时重新核验。

另一次受保护的临时HTTP实跑完成QQ唯一ComboBox→ValuePattern.Value→字符串投影，实际HTTP服务后代worker调用3525.1ms；整轮helper40027.980ms，Job同样归零。它证明该getter成功链，不证明HTTP setter或已安装8765服务；后者在改名前这轮实测时未监听、未部署/重启；DeskWeft改名后的独立服务验收另见交接稿§0.1，不反向补成旧GUI的HTTP setter证据。另以真实2秒deadline验证无GUI runner及普通后代在本次Job内终止并归零，不能推广为任意QQ provider超时的可靠取消。全部成功、失败、源码边界、成本和事件分别保存在独立报告，不拼接跨轮证据。

微信4.2.0.13本轮MCP已检查显示前后根与归属明确的内容child，仍只得空树/单Pane；Ctrl+F返回成功但前后PNG完全一致，没有足够搜索焦点证据，因此没有继续盲输聊天。独立进程另作直接UIA、MSAA和短StructureChanged listener重读，三目标无新增业务内容；这不是MCP路径或新增公开能力。失败/未知保持局部适用范围，不推广为整个微信无自动化能力；微信隔离桌面等后续试验待独立记录。

### 6.5 私有 desktop 的可观察性不是通用前台模拟

当前helper保留阶段/计数/值摘要、真实worker和目标窗口归属、输入desktop样本、前台事件与Job清理证据，没有实现实时画面预览或接管面板。现有PrintWindow/see的按HWND图像路径可作为只读预览候选：由隔离环境取图，在用户桌面展示图像；仍须单独验证目标应用是否能正确持续绘制、内容隐私、图像时效与完整成本。不能从UIA读取成功推断图像可用，也不能把待实现候选写成工具已可调用。

显式切换输入desktop可让人直接查看/接管，但会占用用户输入环境并改变后台约束；当前helper不调用SwitchDesktop，结束时清理本次执行环境，不保留长期会话。将来接管需要先停止新增自动化、查清在途动作与恢复/清理责任，再按前台路线另行实现和验收。不能为了取得预览而无提示切换desktop，也不能切换后继续把同一时段报告为用户视角的后台。

本轮证明的是QQ具体语义路径留在非输入desktop完成，不是所有前台操作都可后台化。其他UIA/native消息路径需要各自真实效果与范围证据；SendInput、真实鼠标键盘、UAC/安全desktop或其他session不在当前支持结论内。隔离不新增HWND定向的通用键鼠工具；某路径依赖输入desktop、渲染或外部broker而受阻时保留边界，不以“前台可以”推断私有desktop必定可用。

另建Windows交互会话或虚拟机只列为更重的候选，尚未实现或验收；其输入、渲染、权限与资源条件需另行验证。

#### 7.6.1 补充实测（2026-11-08，基础实施时直接观测）

针对上表缺的「活动版本证据」，补测了 QQ 进程结构，得到一条原稿没有的事实：

| 观测对象 | 实测值 | 说明 |
|---|---|---|
| 主进程 exe 路径 | `C:\Program Files\Tencent\QQ.exe` | **不含 `versions/`**，第 4 条路径规则对 QQ 不成立 |
| 主进程 FileVersion | `9.9.19.35469` | 落后于实际运行的构建 |
| 渲染子进程 `--app-path` | `C:\Program Files\Tencent\versions\9.9.22-40824\resources\app` | **唯一指向活动版本** |
| `versions/` 目录 | 仅一个子目录 `9.9.22-40824` | 另有 `channel.json`/`config.json`/`setting.json` 三个非目录 |

结论：**QQ 这类启动器结构里，活动版本的可靠来源是子进程命令行，而不是主进程路径或 FileVersion。** 这修正了交接稿 §3 第 4 条「仅当 exe 实际路径包含 versions/」的适用范围——它对 QQ 会返回 `None`。

证据强度：进程路径与子进程命令行为本机直接观测，可复现；「子进程命令行的版本必然等于产品活动版本」是推断，未做跨版本验证，因此实现时仍需如实标 `source`，并提供「唯一候选目录」的降级路径。

## 8. 本轮明确不做

- 插件加载、任意 Python 执行、数据库、自动实战计数、跨机器记忆同步。
- 自动重启用户应用、把“用户离开”当成授权、把记忆正文当成可自动执行脚本。
- 原始 COM 对象外泄、任意表达式执行、裸跨进程指针传递与无限制 UIA 能力承诺；已知对象投影、公共属性读取和有界同步文本消息在本轮可靠实现范围内。
- 为当前规模先做目录分页、多进程写锁或独立缺口状态机；达到这些条件再扩展。单条正文续读属于本轮能力。

这些约束限定部署方式和可承诺的执行接口，不删除 skill 的软件探索面、memory 中的历史证据或未试方向。遇到工具能力之外的目标，应保留尝试、限制和待探索路线，而不是通过缩减目标宣称框架完成。

完成标准是交接稿 §8 的行为测试和安全 GUI/MCP 回归，不是工具注册成功、断言数量增加或历史实测数字相等。
