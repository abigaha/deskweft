## 3. 待办

### P0 —— 先修方法，不是先修代码

**T1. 后台优先，不许先切前台**
skill 第一节就是四级顺序：后台高效 → 后台低效 → 前台高效 → 前台低效。
之前每一轮都以 `force_foreground` 开场，这是违规。
- 先查 `references/foreground-protection.md`，确认当前有没有**已实现且对目标有效**的防抢焦能力
- 没有保护就不发动作，记缺口，继续后台只读候选
- 只有后台候选都有具体受阻依据、且有前台授权，才降到前台层

**T2. 判定工具要先验证再使用**
- `see` 的 PrintWindow 截图在 QQ 上会返回缓存帧（实测：空闲两次 0 差异，
  真实屏幕 1133964 差异）。**不要用它判断界面是否变化**。
- 用真实屏幕 BitBlt 抓取，或树里的结构标记（如「会话列表」出现/消失）。
- 每次下结论前先做对照组：不动作连拍两次，差异必须为 0。

**T3. 失败要按控件类型收窄**
QQ 9.9.37 实测：导航按钮（Toggle 型）语义无效；**但同一窗口里**
搜索框 `SetValue`、搜索结果的 `Invoke`、分组行的 `ExpandCollapse` 全部有效。
一个控件类型失败 ≠ 应用不支持。

## 4. 已知的坑（血泪）

| 坑 | 后果 | 避免方式 |
|---|---|---|
| 用 `see` 截图判断界面变化 | 得出一堆"0 像素"的假结论 | 用真实屏幕抓取 + 对照组 |
| 用元素数判断动作成败 | 316→166 但屏幕没动的假信号 | 同上 |
| 只看 `ok=True` | provider 假报成功 | 必须验证效果 |
| 从单一控件类型推广 | 错判"QQ 语义不可用" | 按控件类型分别测 |
| 先切前台再测 | 违反 skill 后台优先原则 | 先查保护能力 |
| 部署目录放代码副本 | 改代码不生效 | 只用 editable 安装 |
| plan_id 超过 32 字符 | `invalid plan id` | 用短 id |
| `snapshot()` 解包数量 | `ValueError` | 写完就编译检查 |
